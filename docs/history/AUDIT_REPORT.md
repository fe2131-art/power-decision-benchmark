# Power Equipment and Decision Model Comparison Kit: Re-audit Report

> Historical document from the initial offline audit. For current results see [README](../../README.md) and [results/SUMMARY.md](../../results/SUMMARY.md).

Audit date: 2026-11-09
Scope: the earlier four-method comparison material; the re-audited version is this repository.

## API contracts confirmed from primary sources

- OpenAI Decisions API: `POST /v1/decisions`. As of 2026-11-09, the API reference supports **only `model: gpt-6-luna`**. `gpt-6-luna` is also available in the Responses API. However, do not infer that the processing system or internal structure is the same merely because the **model ID** is the same.
- OpenAI Responses API: `POST /v1/responses`, `text.format.type = json_schema`, strict enum constraints.
- Clef-Flash: public model `Cloudflare/clef-flash`, served via `POST /v1/systemone` through the corresponding SGLang.
- Liquid d1-2B GGUF: `POST /v1/systemone` through a recent llama.cpp (v0.8.0/b11960 or later).

## Audit findings for the earlier kit

| Item | Earlier version | Response |
|---|---|---|
| OpenAI model ID | `gpt-6-luna` on two APIs | **Matches the official specification**. The difference between the APIs is documented, and the decision-side display name was changed to `openai-decisions` |
| Denominator issue 1 | `exact_all_fields` was computed only over successful rows | Added `exact_all_fields_over_planned`, which uses all planned cases as the denominator. Failure counts and not-attempted counts are also listed |
| Denominator issue 2 | Cases with missing probabilities were excluded from the `selective_coverage` denominator | All planned cases are now the denominator. A valid probability distribution for all 3 items is required before acceptance |
| Cost | Could display $0 when Usage was missing | If Usage is unknown or incomplete, the amount is `null`. Estimates and actual billing are clearly distinguished |
| Failure detection | Exit code 0 even when the endpoint was broken | Exit code 2 by default. `--allow-partial` only when partial results are needed |
| Request equivalence | The OpenAI LLM's system instructions and the other methods' state inputs differed subtly | All backends receive the same `shared_input` (common rules + target records) |
| Response handling | Incomplete responses were not explicitly rejected | `incomplete`, `failed`, and `cancelled` are treated as failures |
| Probability distributions | No range or sum checks | Range, finiteness, presence of all categories, and sum ≈ 1 are checked |
| Model inference | Local model weights and the real OpenAI API were not run | **Still not run**. Mock success must not be misrepresented as successful real inference |

## Checks performed

- The 48 synthetic cases match SHA-256 even when regenerated by script (content reproducibility).
- At the time of the earlier audit there were 13 unit tests. The latest version added further tests: four kinds of parsers, per-model endpoints, shared input, metrics, invalid probability values, missing Usage, incomplete responses, and others.
- Simulated HTTP send/receive tests for the four methods (`luna-llm`, `openai-decisions`, `clef-flash`, `d1-2b`): all passed.
- CLI CSV/JSON output test passed using two local mock SystemOne servers.
- With an unreachable server, confirmed `success=0 / planned=2`, `not_attempted=1`, and exit code 2.
- Python syntax check and `--dry-run` JSON generation succeeded.

## Remaining limitations (important)

At this point, we have **not demonstrated that correct performance comparison results are obtained**. Sending requests to the real OpenAI API, inference using the Clef/d1 model weights, GPU startup, and model-specific runtime issues are unverified. The code has been written to match the API specifications and checked only with simulated I/O.

The 48 artificial synthetic cases are limited to use as a "processing method comparison demo" and are insufficient to conclude whether deployment in the field is appropriate or safe. Please re-evaluate accuracy, critical false confirmations of causes, calibration, latency, and cost using development data and independent test data in which Japanese power equipment maintenance records have been re-labeled by domain experts. The LLM generation side does not output option probabilities, so it is excluded from the comparison of ECE, Brier, and threshold-based acceptance rates.

## Fixes added in the final review of the 2026-11-09 10-case version

- **Liquid d1-2B request format**: Following the `/v1/systemone` example in the model card, the default no longer sends the `model` key (it can be specified explicitly with `--d1-model`).
- **Group misclassification**: Fixed the issue where PS-001 was labeled `clear` and PS-031 was labeled `hypothesis`. Recovered and partially normal groups are now separated. The text and correct labels are unchanged.
- **Probability validation**: Rejects non-numeric values, booleans, and duplicate probability candidates. Candidates with missing probabilities are excluded from probability evaluation and automatic acceptance.
- **Stricter API response handling**: OpenAI responses that are still in progress, and unexpected response formats from SystemOne, are treated as failures.
- **Readability of demo results**: Added `case_comparison.csv`, which lists the correct answers for the 10 cases alongside each model's predictions. Input strings that could be interpreted as spreadsheet formulas are neutralized in the CSV.
- **README**: Corrected navigation to the 10-case version, `--limit 10`, the commands, and the note that real inference has not been verified.

**The correct labels were assigned by the author of this material; they have not been independently reviewed by power equipment experts.** Expert review is required before any practical use.
